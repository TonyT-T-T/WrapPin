# WrapPin 位置偏差：成因与修复方案

调研分支：`codex/location-accuracy-research`。本方案基于苏州中心广场同机测试，面向现有固定位置、收藏与历史、会话恢复、地图选点和路线模拟链路。Build 22 是单点验证包，不是通用修复版。

## 1. 本次问题怎样产生

用户输入 `31.316633, 120.677664`，WrapPin 的地图图钉指向苏州中心广场，但启动模拟后 Apple 地图蓝点在其东南方向。这个数字与[高德的苏州中心广场地点坐标](https://ditu.amap.com/place/B0FFG1H9ZD)完全相同；[高德文档](https://lbs.amap.com/api/javascript-api-v2/guide/transform/convertfrom)说明高德坐标属于 GCJ-02，而 [Apple 的 Core Location 坐标定义](https://developer.apple.com/documentation/corelocation/cllocationcoordinate2d?language=objc)使用 WGS84。同一组经纬度数值在两种坐标系中指向不同地面位置。

当前 `MapViewModel.coordinateInput` 只解析两个 `Double`，`LocationTarget` 只保存数字，`AppModel` 再将它原样交给 `LocalDeviceSessionCoordinator`；后者把数字传入 `wp_location_session_update`/模拟服务。整个链路没有记录输入坐标系，因此本次把 GCJ-02 的地点数值当作 WGS84 位置发送了。

真机证据将这一解释与“传输精度不够”区分开：Build 21 中模拟目标与 WrapPin 收到的 Core Location 回调均为 `31.316633, 120.677664`，数值距离 0 米。Build 22 将同一地点反算为 WGS84 候选值 `31.318719, 120.673397` 后，回调再次与候选值一致，Apple 地图蓝点移到苏州中心商场区域。两组坐标相距约 467 米，方向与原截图一致。截图只能确认区域和方向，不能据此给出蓝点与建筑物之间的精确误差。回调中的 `5 m` 是系统报告的水平精度字段，不代表图钉与建筑物实测相差 5 米。

这组 A/B 试验强烈支持**WrapPin 地图显示位置与系统模拟位置的坐标解释不一致**。用户又报告地图点选也有同样偏差，因此产品语义应统一为“模拟我在 WrapPin 地图上看到并选中的地点”。MapKit 搜索、点选和路线折线的原始数值仍需分别测量，不能把本次手输试验当作所有入口已验收。

用户观察到国外模拟位置偏差较小但仍存在。这与“中国大陆相关坐标变换解释苏州的大偏移”并不矛盾，也说明不能把所有偏差都归为 GCJ-02。国外样本尚无原始回调、显示比例尺和可复核的距离；需要单独判断是设备收到的数字不同，还是地图蓝点、图钉、道路吸附或地点中心的显示差异。国外现有直通路径应作为回归基线。

## 2. 修复原则

**统一 WGS84 的位置在设备发送端，而不是输入端。** 目前 `LocationTarget.latitude/longitude` 已被原样送进模拟服务，效果就是把所有输入数字都当作 WGS84；苏州样本正是在这种实现下偏移。Build 22 是先将 `31.316633, 120.677664` 换算成 `31.318719, 120.673397` 再发送，才让蓝点回到商场区域。如果把一组本来就是 WGS84 的数字也无条件做 GCJ-02 反算，就会制造相反方向的新偏差。因此设备端保持 WGS84 是确定的，输入端是否需要换算必须由该入口的实际坐标含义决定。

**下一次对照不需要另做“统一 WGS84”包。** 现有 Build 22 已在苏州把 WGS84 候选值送入系统，国外的原值直通也是 WGS84 假设。更有判别力的试验是在当前包里选一个用户已观察到小偏差的国外**具体点位**，保持固定模拟，读取新的 Core Location 回调，并同时记录 WrapPin 图钉、Apple 地图蓝点和地图比例尺：若目标与回调数字一致，问题在数值发送之后的地图呈现或地点定义；若数字不一致，再查会话更新、缓存与定位来源。不要拿两个名称相近但中心点不同的 POI 当作同一个坐标比较。

1. WrapPin 的**地图图钉是用户要模拟的地点**。搜索、地图点选、手输坐标最终都先落实到这个图钉；输入框不要求用户声明 GCJ-02 或 WGS84，也不提供常驻坐标系选择。用户只需确认图钉落在想去的地方。
2. `LocationTarget` 继续表示地图选中的目标，保留地图标记、名称、收藏、历史和复制坐标的现有语义。在送入设备模拟前，统一计算这个地图地点对应的 WGS84 坐标；设备坐标是派生值，不反写为用户的目标，不在界面展示为“另一个需要输入的坐标”。诊断页可显示它，便于排查。
3. 对经真机证实使用 GCJ-02 数值的中国大陆选点入口，在送出前转为 WGS84；本次苏州目标应送出约 `31.318719, 120.673397`。已是 WGS84 的入口与大陆外目标直通。规则由入口的实测语义确定，不能只看经纬度是否位于中国大陆，也不能使用固定米数平移；转换只发生在发送出口，不在搜索、逆地理编码、收藏或地图重绘时重复执行。
4. 旧版收藏和历史保存的是用户选中的地图地点，重新模拟时也走同一个地图地点→设备坐标规则；无须用户重新输入或逐条迁移。固定会话恢复同理。若某条旧记录的图钉本身不在用户想要的位置，它属于选点问题，应让用户在地图上重选，而非暗中猜测数字来源。
5. `MapProxy.convert`、`MKLocalSearch` 和手输选点的返回值分别做同机 A/B，确认各自数字和图钉的关系；统一的是**“按图钉所在地点模拟”这一行为**，实现时不假定三个 API 返回值一定同属一种坐标系。路线折线另行验证，不把固定点的转换规则未经测量地套到所有路线点上。

## 3. 按当前代码落地

| 改动处 | 具体工作 |
| --- | --- |
| `LocationTarget` 与本地存储 | 固定目标继续表示地图图钉，无需给用户增加坐标系字段或迁移旧收藏/历史。内部若需区分路线折线点与固定地图目标，使用明确类型或来源标记，防止误用转换函数。 |
| `MapViewModel` 与坐标输入 UI | 手输、搜索、点选都先形成可见图钉；用户按图钉确认地点。逆地理编码只补地点文字，不能把设备坐标写回地图目标。 |
| `AppModel` 与 `LocalDeviceSessionCoordinator` | 在固定会话启动、更新和恢复的共同出口，从地图目标派生 WGS84 设备坐标。UI 活跃地点仍指向原始图钉；收藏、历史与复制坐标不被设备值覆盖。诊断区分已排队更新与新鲜 Core Location 回调。 |
| `SessionRecoveryRecord` | 保存用户的地图目标；恢复固定会话时重新派生一次设备坐标。旧记录按同一规则恢复，停止按钮与选中卡片仍按地图目标匹配。 |
| Build 22 试验入口 | 通用转换完成并验证后移除苏州硬编码按钮；保留可读取原始回调的诊断能力。 |

**路线单独处理。** `WalkingRoutePlanner` 用 MapKit 规划，`WalkingSimulationController` 将 `MKRoute` 折线点逐个送往设备。先测清折线点及路线起终点的坐标含义，再让路线每个发送点通过相同的明确规则；同时测首点与选定起点、末点与目的地的距离。不能只转换终点或只转换固定位置，否则会在开始、移动或到达时跳点。路线预览继续使用其原始 MapKit 几何，设备发送值另算。

## 4. 实施与验收顺序

1. **先修固定位置的共同发送出口。** 将地图目标与设备坐标分开，完成 GCJ-02→WGS84 派生函数，覆盖启动、活跃更新及恢复；单元验证苏州样本的转换与逆向回算、大陆外直通、旧收藏重用及恢复不重复转换。
2. **同机确认各选点入口。** 在同一台 iPhone 上用手输、地图点选和搜索分别选苏州中心，记录各自的图钉坐标、送出值和新鲜 Core Location 回调，确认三种方式最终都落在同一个地点。若某入口的数字语义不同，在该入口与设备坐标派生之间做内部适配，用户体验仍是选哪儿到哪儿。
3. **真机回归。** 再测另一个中国城市、大陆以外地点、旧收藏和历史、活跃更新与应用重启恢复。验收以图钉与 Apple 地图蓝点落在同一地点区域、新鲜回调等于预期设备坐标为准；截图不能证明米级精度。
4. **最后处理步行与驾车路线。** 对折线首点、中点、末点记录设备值与回调，检查整条路线、到达瞬间和会话恢复；与固定位置一起完成回归后再准备正式发布包。

发布门槛：自动化测试通过，实际安装的新包完成上述真机矩阵，且旧版收藏/历史/恢复都按地图图钉对应的地点模拟。当前 Build 22 只完成了苏州手输固定点的方向验证；地图点选、搜索与路线仍需同机验收，它本身不满足正式修复验收。
