# WrapPin 位置偏差：成因与修复方案

调研分支：`codex/location-accuracy-research`。本方案基于苏州中心广场同机测试，面向现有固定位置、收藏与历史、会话恢复、地图选点和路线模拟链路。Build 22 是单点验证包，不是通用修复版。

## 1. 本次问题怎样产生

用户输入 `31.316633, 120.677664`，WrapPin 的地图图钉指向苏州中心广场，但启动模拟后 Apple 地图蓝点在其东南方向。这个数字与[高德的苏州中心广场地点坐标](https://ditu.amap.com/place/B0FFG1H9ZD)完全相同；[高德文档](https://lbs.amap.com/api/javascript-api-v2/guide/transform/convertfrom)说明高德坐标属于 GCJ-02，而 [Apple 的 Core Location 坐标定义](https://developer.apple.com/documentation/corelocation/cllocationcoordinate2d?language=objc)使用 WGS84。同一组经纬度数值在两种坐标系中指向不同地面位置。

当前 `MapViewModel.coordinateInput` 只解析两个 `Double`，`LocationTarget` 只保存数字，`AppModel` 再将它原样交给 `LocalDeviceSessionCoordinator`；后者把数字传入 `wp_location_session_update`/模拟服务。整个链路没有记录输入坐标系，因此本次把 GCJ-02 的地点数值当作 WGS84 位置发送了。

真机证据将这一解释与“传输精度不够”区分开：Build 21 中模拟目标与 WrapPin 收到的 Core Location 回调均为 `31.316633, 120.677664`，数值距离 0 米。Build 22 将同一地点反算为 WGS84 候选值 `31.318719, 120.673397` 后，回调再次与候选值一致，Apple 地图蓝点移到苏州中心商场区域。两组坐标相距约 467 米，方向与原截图一致。截图只能确认区域和方向，不能据此给出蓝点与建筑物之间的精确误差。回调中的 `5 m` 是系统报告的水平精度字段，不代表图钉与建筑物实测相差 5 米。

这组 A/B 试验强烈支持**本次手输高德坐标与模拟服务的坐标系混用**。它没有证明 MapKit 搜索、地图点选或路线折线都返回 GCJ-02；这些入口不能直接套用同一转换。

## 2. 修复原则

1. 每个目标保存**原始坐标、坐标系、来源**。坐标系至少区分 `WGS84`、`GCJ-02`、`未确认`；来源区分手输、MapKit 搜索、地图点选、路线和旧版记录。来源与坐标系是两个字段，不能通过经纬度大小或所在城市猜测坐标系。
2. 地图标记、地点名称、复制坐标与用户选中的原始目标保持一致；另算一个**实际送往设备的 WGS84 坐标**。只在统一的模拟发送边界转换一次，并在诊断页同时显示两组数值与所用规则。
3. 手输坐标提供明确选择：`GPS / WGS84` 与 `高德等地图 / GCJ-02`。本次样本选择 GCJ-02 时，模拟值应接近 `31.318719, 120.673397`；选择 WGS84 时原值直通。已有手输行为默认直通，不能在升级后静默改变旧坐标的意义。可以记住用户上次明确选择，但要在开始模拟前可见。
4. MapKit 搜索和地图点选先保留当前直通行为，同时分别记录返回值、图钉和真机回调，对已知地点做对照；仅当某入口被证实需要转换时，给该入口赋予经验证的坐标系规则。MapKit API 类型本身不能当作中国大陆真实呈现行为的完整证据。
5. GCJ-02→WGS84 使用有边界检查的纯计算函数，验证参考样本、逆向回算与异常输入；不使用固定米数平移，也不根据中国大陆经纬度范围自动转换所有数据。转换失败时提示用户，不静默使用另一种含义的坐标。

## 3. 按当前代码落地

| 改动处 | 具体工作 |
| --- | --- |
| `LocationTarget` 与本地存储 | 增加输入坐标系和来源；自定义 `Codable` 兼容旧版收藏、历史与 `SessionRecoveryRecord`，缺失字段解码为“旧版未确认、原值直通”，不批量改写旧记录。相同数字但坐标系不同的目标须可区分；改名、逆地理编码刷新时保留元数据。 |
| `MapViewModel` 与坐标输入 UI | 手输坐标附带来源选择；搜索、点选分别标记来源。逆地理编码只补地点文字，不能丢弃坐标系。地图标记仍依据原始选点，复制坐标时显示坐标系。 |
| `AppModel` 与 `LocalDeviceSessionCoordinator` | 在启动、更新和恢复会话的共同出口生成 WGS84 模拟坐标；传给原生会话的是转换结果，UI 活跃地点仍指向原始目标。不能把转换后的数值反写到收藏或历史，也不能在恢复时再次转换。更新成功状态与原生服务真正应用坐标的诊断区分显示。 |
| `SessionRecoveryRecord` | 保存用户目标与其坐标系；恢复固定模拟时重新计算一次 WGS84 设备坐标。迁移旧记录保持原值直通。恢复中的显示地点、停止按钮与选中卡片不能因设备坐标不同而失配。 |
| Build 22 试验入口 | 通用转换完成并验证后移除苏州硬编码按钮；保留可读取原始回调的诊断能力。 |

**路线单独处理。** `WalkingRoutePlanner` 用 MapKit 规划，`WalkingSimulationController` 将 `MKRoute` 折线点逐个送往设备。先测清折线点及路线起终点的坐标含义，再让路线每个发送点通过相同的明确规则；同时测首点与选定起点、末点与目的地的距离。不能只转换终点或只转换固定位置，否则会在开始、移动或到达时跳点。路线预览继续使用其原始 MapKit 几何，设备发送值另算。

## 4. 实施与验收顺序

1. **先修固定位置。** 完成坐标系数据模型、手输选择、转换、存储迁移、启动/更新/恢复的统一发送出口；移除苏州硬编码试验入口。单元验证 GCJ 样本的转换与逆向回算、WGS 原值直通、旧记录原值直通，以及一次转换后恢复不重复转换。
2. **真机验收固定位置。** 在同一台 iPhone 上重测苏州 `31.316633, 120.677664`（GCJ-02）、一个明确来源为 WGS84 的中国坐标、另一个中国城市以及中国大陆以外坐标。每次记录原始目标、送出值、Core Location 回调及 Apple 地图蓝点；固定点、活跃更新、应用重启恢复都要过。数值验收以送出值与新鲜模拟回调一致为准；地图截图验收是落在预期地点区域，不承诺仅凭截图达到米级。
3. **再处理地图搜索、点选。** 对各入口记录原始返回值并做 A/B 真机验证；确认后才设定该入口的自动转换规则。无法确认时保持直通并向用户明确显示坐标系选择，避免“看起来自动修好”却把已有 WGS84 点再次偏移。
4. **最后处理步行与驾车路线。** 对折线首点、中点、末点记录设备值与回调，检查整条路线、到达瞬间和会话恢复；与固定位置一起完成回归后再准备正式发布包。

发布门槛：自动化测试通过，实际安装的新包完成上述真机矩阵，且收藏/历史/恢复不改变旧记录含义。当前 Build 22 只完成了第一组苏州固定点的方向验证；它本身不满足正式修复验收。
